# Jump Capability Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a one-shot, key-triggered jump to the `open_duck_mini_v2` joystick environment, learned by a single policy that also walks.

**Architecture:** A new `cmd[7]` jump flag extends the command vector to 8 (observation 101 -> 102). A shared two-state window/cooldown timer, implemented once in backend-agnostic arithmetic, drives that flag in both JAX training and numpy inference. Three new reward terms fire only while the window is open; three existing terms are gated down so they stop fighting the jump.

**Tech Stack:** JAX 0.8.3, MuJoCo MJX 3.12, Brax 0.14.2 PPO, `playground` (mujoco_playground) 0.0.5, pytest, uv.

**Spec:** `docs/superpowers/specs/2026-08-31-jump-design.md`

## Global Constraints

- Python 3.12 (TensorFlow ships no cp314 wheels; `uv python pin 3.12` is already set).
- `jax>=0.5.0,<0.9` — jax >=0.9 removed `jax.device_put_replicated`, still called by brax 0.14.2.
- `playground==0.0.5` — later versions deleted `mujoco_playground._src.collision`.
- Scope is sim-only. Do not add sim-to-real machinery.
- Every jump reward term must be exactly `0.0` when `jump_active == 0.0`. This is the regression guarantee that walking behaviour is unchanged.
- Window and cooldown constants live in exactly one module, `playground/open_duck_mini_v2/jump.py`. Never duplicate their literal values into `joystick.py` or `mujoco_infer.py`.
- All new environment tunables go in `default_config()` as config entries, not module-level constants.

```python
"""Shared jump timing for training (JAX) and inference (numpy).

The state machine is deliberately backend agnostic: it uses only arithmetic and
comparison operators, never `jax.numpy` or `numpy` calls, so one implementation
runs under JAX tracing and under plain numpy. That is the point -- if training
and inference disagreed about the window length, the policy would see a
different command profile at inference than it trained on and the jump would
silently degrade.
"""

# Control rate is 50 Hz (ctrl_dt = 0.02).
JUMP_WINDOW_STEPS = 40  # 0.8 s: crouch, flight and landing with margin
JUMP_COOLDOWN_STEPS = 50  # 1.0 s: blocks re-trigger while recovering


def advance_jump(timer, cooldown, trigger):
    """Advance the jump state machine by one control step.

    Branchless so it can be jitted and vmapped.

    Args:
      timer: control steps left in the current jump window; 0 when idle.
      cooldown: control steps left before another jump may fire; 0 when ready.
      trigger: 1 when a jump is requested this step, 0 otherwise.

    Returns:
      ``(timer, cooldown, active)`` for the next step. ``active`` is 1.0 while
      the window is open and is what becomes ``cmd[7]``.
    """
    # A jump may only start from a full stop: no window open, no cooldown left.
    idle = (timer <= 0) * (cooldown <= 0)
    fire = idle * (trigger > 0)

    # `(timer - 1) * (timer > 0)` floors at 0 without needing a backend max().
    decayed_timer = (timer - 1) * (timer > 0)
    next_timer = fire * JUMP_WINDOW_STEPS + (1 - fire) * decayed_timer

    # The window ends on the step where the timer was about to hit zero.
    window_ended = (timer == 1) * (1 - fire)
    decayed_cooldown = (cooldown - 1) * (cooldown > 0)
    next_cooldown = (
        window_ended * JUMP_COOLDOWN_STEPS + (1 - window_ended) * decayed_cooldown
    )

    active = (next_timer > 0) * 1.0

    return next_timer, next_cooldown, active
```

In `_get_reward`, after the `ret = { ... }` dict literal and before `return ret`,
insert:

```python
        jump_active = info["jump_active"]
        base_z = data.qpos[self._floating_base_qpos_addr + 2]
        base_vz = data.qvel[self._floating_base_qvel_addr + 2]
        grounded = jp.any(contact)
        airborne = jp.all(~contact)

        # Dense bootstrap term: reward pushing upward while a foot is still
        # down. Without this the height reward is never discovered, because a
        # walking policy never leaves the ground by accident.
        ret["jump_takeoff"] = (
            jp.clip(base_vz, 0.0, jp.inf) * grounded * jump_active
        )
        ret["jump_air_time"] = airborne * jump_active
        ret["jump_height"] = (
            jp.clip(
                base_z - self._config.nominal_base_z,
                0.0,
                self._config.jump_height_cap,
            )
            * jump_active
        )

        # Gate the terms that would otherwise fight the jump.
        # imitation pins joints to a walking reference at weight 15.
        ret["imitation"] = ret["imitation"] * (1.0 - jump_active)
        # stand_still punishes joint motion when the velocity command is ~0,
        # which would penalise a jump in place.
        ret["stand_still"] = ret["stand_still"] * (1.0 - jump_active)
        # action_rate at -0.5 suppresses the fast action changes a jump needs.
        # Soften rather than remove, or the motion gets jittery.
        ret["action_rate"] = ret["action_rate"] * (1.0 - 0.5 * jump_active)
```

```python
                                self.motor_targets,
                                self.prev_motor_targets
                                - max_motor_velocity
                                * (self.sim_dt * self.decimation),
                                self.prev_motor_targets
                                + max_motor_velocity
                                * (self.sim_dt * self.decimation),
                            )
```

## Self-Review Notes

**Spec coverage.** Every spec section maps to a task: interface change -> Task 2;
state machine -> Tasks 1 and 2; rewards and gating -> Task 3; height ceiling ->
Task 4; train/inference drift -> Tasks 1 and 5; inference and viewer -> Task 5;
verification and risks -> Task 6.

**Deliberately deferred.** The spec lists `jump_peak_z` and `jump_took_off` as
`state.info` fields. Neither is needed: `jump_height` rewards height continuously
rather than at apex, and `jump_air_time` reads live contact instead of a latch.
Adding unused state would be dead weight. If a future apex-only reward is wanted,
they can be added then.
